# 3 Data research and interactive experience

This supporting specification defines the evidence and interface required for SupplyLens, a master's project combining retail forecasting, inventory simulation, document retrieval, and supervised agent workflows. Requirements below are proposed project decisions; the source register distinguishes externally verified dataset and technology facts. The initial repository is empty and real datasets will be supplied later. Do not report data inspection, trained models, measured improvements, or completed integrations before producing the corresponding evidence. Gate P0 means a controlled product; P1 means an enterprise pilot; P2 means qualified production. These are release gates, not issue severity labels.

## Data admission and provenance

DAT-001  -  Discover the supplied inputs without changing them. Inspect the nominated project and input directories only. Inventory supported tables, archives, documents, and accompanying licenses before selecting an adapter. Create a manifest with original filename, relative location, file type, byte size, SHA-256 hash, acquisition and ingestion timestamps, and dataset version. Keep original files immutable; extract archives into a separate staging area with safe path handling. Do not execute embedded scripts, spreadsheet macros, or document instructions. Produce processed copies with reproducible transformations, hashes, and an exclusion log. A failed import must leave the originals intact.

DAT-002  -  Record permissions per file, not merely per repository. Each manifest entry must carry source URL or supplied-owner attribution, license identifier and exact terms reference, permitted purpose, redistribution conditions, sensitive fields, and unresolved restrictions. Record unknown permissions as unknown. A public download or an MIT-licensed adapter does not establish permission to redistribute its upstream business data. P0 may use authorized local data without republishing it. P1 and P2 require documented rights for their intended use. Never silently replace missing real inputs with generated records.

DAT-003  -  Publish a schema and quality report before modeling. For each table, record column meaning, datatype, units, currency, timezone, cadence, primary and foreign keys, event time, available-at time where known, row count, date span, missingness, duplicates, and invalid values. Report cancellations, returns, negative quantities, product-code changes, partial periods, and missing calendar coverage explicitly. An ingestion timestamp is not proof that a historical fact was available to a planner at that time. Preserve that distinction in backtesting and document it when historical availability cannot be reconstructed.

DAT-004  -  Select one primary source population. Prefer suitable user-supplied real data. Otherwise, assess M5 and UCI Online Retail II independently. Use one as the principal forecasting dataset and retain a separate dataset ID for every additional study. M5 contains item-store sales and calendar/price information; the organizers also publish evaluation resources. UCI Online Retail II contains transactions for one UK online retailer and is licensed CC BY 4.0. [D1][D2] Do not combine Walmart, the UCI retailer, and H&M articles into one supposed enterprise. A common adapter schema permits comparable software behavior, not a fictional common business history.

For M5, verify competition access and dataset terms at acquisition. Preserve its item/store hierarchy and calendar mapping. Its supplied retail data do not establish supplier purchase costs, purchase orders, on-hand inventory, actual lead times, or warehouse geometry. For UCI, the documented period is December 2009 to December 2011; invoice codes beginning with C indicate cancellation, prices are sterling, and Country describes customer residence. [D2] Country must not become a warehouse identifier. Use actual product codes, retain returns separately, and define whether the target is fulfilled positive units or net transactions. Explain exclusions rather than dropping all inconvenient rows.

DAT-005  -  Keep InventoryBench in the correct role. Its documented histories contain five periods; the real-data configuration uses five training weeks and 48 evaluation weeks. Cost/lead-time variants reuse underlying trajectories. [D3] This is useful for a separate agent/control benchmark, not an adequate primary history for training the proposed deep forecasting model. Never train on benchmark test trajectories or count variants as independent demand histories. Group by underlying article/trajectory. Verify upstream H&M terms separately from the repository's MIT license. Its README and detailed specification describe different reward denominators; pin and inspect the actual evaluator before reproducing a score. [D3][D4]

DAT-006  -  Preserve the distinction between sales and demand. Transactions measure observed sales. Without reliable availability records, a zero may represent no purchases, missing extraction, closure, an unlisted item, or a stockout. Label the model output "unit-sales forecast" unless uncensored demand is justified. Do not interpolate lost demand as a discovered fact. If historical sales drive inventory simulation, label them a demand proxy and discuss how unmet purchases may be absent. Claims about actual stockout reduction or business ROI require additional evidence beyond this retrospective proxy simulation.

DAT-007  -  Maintain explicit canonical contracts. Forecast observations require tenant, dataset snapshot, real series/product/location identifiers, event date, observed units, source-row lineage, and availability information. Preserve missing location or inventory fields as missing. Optional stock ledgers, supplier terms, orders, receipts, and costs have separate tables and permissions. Documents require source, document/version ID, hash, page or section locator, effective dates, tenant scope, and access scope. Currency conversion, aggregation, and derived fields must retain their calculation version and contributing sources. A data card records which operational questions the admitted data can and cannot answer.

## Forecasting and dissertation protocol

ML-001  -  Freeze a feasible task after admission. Use daily forecasting with a 28-day horizon as the initial design for suitable retail histories; change cadence or horizon only through a documented decision based on the supplied data and planning interval. Define a minimum usable history, missing-period policy, seasonal period, training cohort, and cold-start policy before inspecting test outcomes. Start with a reproducible, moderately sized cohort, then expand if compute permits. Select that cohort using information available in training, not total future sales. If the data cannot support the DL study, report the shortfall and use an authorized fallback dataset rather than inventing observations.

ML-002  -  Implement exactly three principal model families. Compare seasonal naïve, LightGBM, and one compact temporal convolutional network (TCN). Train the LightGBM and TCN on the admitted data; save their actual learned artifacts. LightGBM supports a quantile objective, and the original TCN paper motivates causal convolutional sequence models. [D5][D6] Neither source guarantees that either model will outperform seasonal naïve here. Use quantiles 0.10, 0.50, and 0.90. The median is the common point forecast. The student must own the feature pipeline, training code, configuration, evaluation, and interpretation; a hosted LLM answer does not satisfy this training requirement.

Keep the TCN compact: causal dilated residual blocks, a declared context window, a small channel budget, dropout, and a direct multi-horizon quantile head. Choose its receptive field to cover the intended context. Tune a bounded set of hyperparameters on validation data. Use the same permitted covariates, horizons, series, and evaluation origins for all models. Estimate seasonal-naïve uncertainty from training-only historical errors with a documented method; do not give it future residuals. Any clipping of impossible negative unit predictions, quantile rearrangement, or calibration must be declared and applied consistently before final scoring.

ML-003  -  Prevent temporal and group leakage. Fit imputers, encoders, scalers, feature selection, and calibration only on the appropriate training partition. Shift rolling features before the forecast origin. Use future calendar information only when actually known; observed future prices, revised orders, and realized lead times are unavailable unless an authentic advance schedule proves otherwise. Avoid random splits of overlapping windows. Exact duplicates and trajectory variants stay together. A chronological test on existing SKUs measures operational forecasting; a separate held-out SKU/location experiment measures transfer. Do not describe one as the other.

ML-004  -  Keep an untouched final test. Define chronological training, validation, and final-test dates from the actual data. Use rolling origins for development and exclude training examples whose forecast labels cross the training cutoff. Freeze model selection, hyperparameters, preprocessing, aggregation, and metric definitions before the final test. Record whether an operational walk-forward protocol allows scheduled refits using newly available observations. Run the same protocol for every model. Aim for at least three TCN seeds within the compute budget, recording hardware, duration, peak memory, and any failed runs. Use paired comparisons on identical origins; uncertainty estimates should respect dependence across series and time blocks rather than treating every row as independent.

ML-005  -  Evaluate point accuracy and uncertainty honestly. Report MAE and MASE for point forecasts, with the seasonal-naïve scale computed from training data. If that denominator is zero, or insufficient history prevents its definition, mark MASE undefined, report the affected series count, and retain MAE; never hide the issue behind an arbitrary epsilon. State aggregation weights and metric coverage. Report pinball loss separately for each quantile and horizon, empirical coverage and width for the central 80% interval, and quantile-crossing frequency. Forecast evaluation and scaled errors are established in the authors' forecasting text. [D7] Treat subgroup calibration and intermittency as substantive findings. Percentage metrics with zero denominators cannot be silently averaged away.

Do not obtain a lead-time demand quantile by summing daily quantiles and calling it calibrated: temporal dependence matters. If the optimizer needs multi-day uncertainty, use an explicitly validated aggregate-demand model or scenario-generation method that preserves relevant dependence, such as training-residual blocks. Record its assumptions and calibration separately. Until this is implemented, restrict claims to the evaluated marginal forecasts and clearly identified simulation scenarios.

ML-006  -  Separate the two experimental questions. For the forecasting comparison, hold the optimizer, constraints, cost assumptions, initial conditions, and scenario shocks fixed while varying only the forecast model. For the RAG/agent comparison, freeze the selected forecaster and the same optimizer. Compare a deterministic tool workflow, basic vector retrieval, hybrid retrieval with reranking and metadata filters, and an adaptive agent using that same enhanced retrieval. Give each applicable condition equivalent permissible documents and as-of information. Keep extraction, retrieval, and tool policies explicit so differences can be attributed. An optimizer must enforce feasibility; the LLM must not invent arithmetic or bypass constraints.

Use a held-out, human-reviewed question/action set for retrieval recall, citation entailment, numeric correctness, handling of conflicting or expired documents, appropriate abstention, tool/task success, latency, and token cost. Include missing information and cross-tenant access attempts. Freeze ground truth and scoring rules before comparison. Supplement automated checks with human assessment; an LLM judge alone is insufficient. Preserve negative results. A convincing dissertation may show that better forecasts help inventory decisions while extra agent complexity does not improve a particular task.

ML-007  -  Specify the inventory simulator before claiming business benefit. Default to a lost-sales system. Declare the order of events: observe permitted state, choose orders, receive any due deliveries according to the stated zero-lead-time convention, realize demand, fulfill up to available stock, record lost sales, then accrue holding cost. Define start stock, pipeline, lead-time distributions, review interval, order horizon, unit/case-pack rules, minimum order quantities, capacity, budget, and costs. Preserve nonnegative physical inventory and identify infeasible plans explicitly. Selling price is not purchase cost. When these inputs are absent, create a separately versioned assumption configuration, visibly labeled simulated, with rationale and sensitivity ranges.

Compare policies under the same initial state and paired random shocks; agents cannot inspect future demand or realized future lead times. Report fill rate against the stated demand proxy, stockout periods, average inventory, ordering/holding/shortage costs, feasibility violations, and a service-cost tradeoff. Show sensitivity to lead-time and cost assumptions. A perfect-foresight reference is an oracle bound, not a deployable policy. Do not translate simulated savings into actual ROI or causally attribute outcomes to the product without an appropriate field study.

ML-008  -  Make every result reconstructable. Save dataset and document hashes, cohort and split manifests, feature configuration, model checkpoints, dependencies, seeds, forecast files, simulator version, optimizer settings, assumptions, and evaluation outputs under an experiment ID. Export a model card, data card, metric dictionary, and limitations statement. Research figures must identify observed, predicted, and simulated quantities. The app must load measured experiment results, not handwritten scores. P0 acceptance requires a reproducible end-to-end study on authorized data; P1 and P2 add evidence required for their actual operating context rather than relabeling the dissertation demonstration as production.

## Visual system and shared product state

UX-001  -  Establish a distinctive, restrained identity. SupplyLens should feel like a professional planning instrument: graphite structure, warm off-white surfaces in light mode, clear typography, teal selections, cobalt forecast lines, and amber risk cues. Use tabular numerals, disciplined alignment, readable density, and quiet section divisions. Suggested starting tokens are light background #F7FAF9, surface #FFFFFF, text #172B27, muted #536B63, accent #147A62; dark background #10191B, surface #172225, text #E8F0ED, muted #A7BCB4, accent #63C9A8. These are proposals requiring contrast verification, not certified combinations. Reserve stronger color for decisions and state; encode meaning with text and shape as well.

UX-002  -  Implement Light, Dark, and System completely. Persist the explicit selection, follow operating-system changes only in System mode, avoid a wrong-theme flash, and style controls, dialogs, tooltips, charts, loading states, focus outlines, and 3D materials coherently. Browser color-scheme preferences support this behavior. [D8] Use semantic application tokens rather than scattered hardcoded colors. Theme changes must preserve filters, chart zoom, selection, draft text, and scenario state. Provide a readable print/export theme. Test every state in both themes, including disabled and destructive controls.

UX-003  -  Share one trustworthy context across every widget. The canonical state contains tenant ID, dataset snapshot ID, reporting range, historical as-of cutoff, timezone, currency, scenario ID/version, forecast/model run, product/location selection, and active filters. Serialize appropriate non-sensitive state in the URL. Scope caches, APIs, saved views, document retrieval, and exports to tenant and permissions. A tenant change cancels outdated requests and clears unauthorized selections; historical snapshots must not appear current because today's date is displayed. Changing a date filter must change the underlying query, with the as-of cutoff distinguished from the chart's visible range.

Every KPI, table, chart mark, 3D selection, chat citation, and export must be traceable to a snapshot, calculation/model run, source hashes, and applicable field permissions. Field restrictions apply before aggregation, tool output, and rendering; hidden columns must not leak through tooltips, totals, chat, or exports. If an existing immutable source unexpectedly changes or its lineage breaks, invalidate unreproducible dependent results and show "source changed" or "provenance unavailable" with a repair path. A legitimate new source version preserves historical snapshots and their evidence; it marks current pending plans for refresh without rewriting completed decisions. Do not continue displaying stale derived numbers as current verified outputs. Use concise provenance chips: Observed, Forecast, Assumed, and Simulated.

## Required screens and genuine interactions

UX-004  -  Data admission and overview. An empty installation opens a purposeful setup screen: choose inputs, inspect file/schema previews, map fields, review quality and permissions, and create a dataset snapshot. No fabricated dashboard is shown as a connected business. The overview presents a few relevant, defined KPIs with coverage and last successful refresh. Selecting a KPI filters the associated records and explains its calculation. Missing stock data produces a clear unavailable inventory measure, not zero stock. If an optional tutorial uses synthetic data, it occupies a visibly separate demo workspace.

UX-005  -  Inventory workspace and meaningful 3D. Pair a sortable, filterable inventory/product table with a switchable 2D network and 3D scene. Use real entity IDs and documented relationships. When geometry is unavailable, label the scene "schematic"; do not imply measured warehouse dimensions or geographical distances. A supplier/location/product selection must highlight the corresponding mesh, table row, forecast series, and evidence drawer. Selecting the row must produce the same result. Camera reset, focus-selected, and clear-selection controls have visible labels. Never require canvas picking to perform an essential task.

Use React Three Fiber for the user-selectable scene and Apache ECharts as the single quantitative chart library. ECharts exposes selection and zoom events that can connect charts to application state. [D9] The product must implement those connections explicitly. A time slider moves through actual available snapshots or a named scenario's simulated states; it must not animate invented stock movements. The 3D mode is a required implemented feature on supported desktop devices. A compact 2D table/network provides full functional parity, loads by default on constrained devices, and remains available if WebGL fails. Decorative orbiting objects, perpetual camera motion, and exaggerated risk effects add no business evidence.

UX-006  -  Forecast lab and linked charts. Show observed history, the forecast origin, horizon, median, and labeled 10-90% interval. Link brushing and date zoom to the shared reporting state without feedback loops. Selecting a product updates forecasts, error tables, and metadata together. Model comparison uses identical folds and shows measured pinball/MAE/MASE coverage with definitions. Label axis units and currencies; represent missing dates as missing, not false continuity. Legends, pinned tooltips, drilldowns, and reset controls work with keyboard and touch. Every chart has a useful text summary and accessible data table. Display downsampling must not alter analytical results or exports.

UX-007  -  Scenario studio. Provide bounded inputs for assumptions such as supplier delay, demand multiplier, budget, and service target only where the implemented model supports them. Each control shows units, baseline value, allowed range, and provenance. A local edit creates a draft scenario; recomputation uses the actual simulator/optimizer and shows pending status. Compare the baseline and draft under the same snapshot and shocks. Display plan quantities, feasibility, constraint explanations, and changes in simulated service/cost. Saving creates a versioned scenario. Exporting a draft plan must not imply that a purchase order was sent. Inputs changing after calculation mark the previous result stale until recomputed.

UX-008  -  Evidence copilot and run history. Chat answers cite document versions and page/section locations and link numerical claims to forecast or calculation runs. The evidence drawer shows effective dates and permission-appropriate excerpts. Display concise task states and tool outcomes, such as "forecast available" or "constraint check failed," rather than an invented reasoning transcript. Missing/conflicting evidence prompts a precise limitation or request for the missing input. Run history records actual queued, running, completed, cancelled, and failed jobs, with inputs, duration, artifacts, and reproducible exports. Progress percentages require a real denominator; otherwise use honest stage status.

UX-009  -  Design non-happy paths as complete flows. Loading reserves layout space; empty states explain missing inputs or zero matching records; errors preserve user edits and provide retry or repair. Validate dates, units, ranges, unknown IDs, expired sessions, and incompatible snapshots. Disable impossible actions with a reason. Cancel or supersede stale requests when filters change, and reject late responses for an old tenant/scenario. Refreshing a long job reconnects to its durable job ID. Partial results are labeled partial. A broken document link or forecast artifact is actionable. Avoid optimistic success for order execution or training completion.

UX-013 - Supplier policies and approvals. Provide a searchable supplier and policy workspace with document versions, effective-date filters, side-by-side amendments and affected pending plans. The action drawer must show exact supplier, SKU, quantity, unit, currency, amount, delivery date, environment and evidence. The approval queue supports review, reject with reason, edit and revalidate, expiry, and role-aware escalation. A visible state change is confirmed against the server; unavailable actions explain their prerequisite.

UX-014 - Administration and value reporting. Provide functional screens for memberships and roles, data-source permissions, job history, connector status, model promotion history, tenant usage budgets, retention and audit export. A business-value view compares measured results or explicitly labelled simulated scenarios, with service-cost tradeoffs, objective breakdowns and sensitivity controls. Display price, currency, period and attribution assumptions next to financial values. Do not label a scenario's lower cost as realized customer savings.

## Accessibility  performance  and acceptance evidence

UX-010  -  Target WCAG 2.2 AA and verify real tasks. Use semantic controls, a logical heading/focus order, visible unobscured focus, labels, skip links, and keyboard dismissal with focus restoration. Test text contrast of at least 4.5:1, applicable large text at 3:1, and relevant non-text controls at 3:1. Support 200% zoom and reflow at 320 CSS pixels. WCAG's minimum target-size criterion is 24 CSS pixels with exceptions; prefer 44-pixel touch targets where feasible. [D10] Announce meaningful calculation completion politely without reading every slider frame. Chart ARIA descriptions and patterns help but do not replace keyboard-operable controls and data tables. [D11]

Honor reduced-motion preferences and offer pause controls where motion communicates time. [D12] Remove idle rotation, strong parallax, and repeated entrance animation. Users must be able to inspect the same scenario in a static view. Test native range controls and numerical alternatives, accessible comboboxes, table navigation, dialog focus, and validation messaging. Use manual keyboard and screen-reader journeys alongside automated checks; a passing automated scan is not proof that complex analytical tasks are accessible.

UX-011  -  Set measurable performance targets. Target field 75th-percentile LCP at or below 2.5 seconds, INP at or below 200 milliseconds, and CLS at or below 0.1 where field measurement exists. [D13] Label pre-release results as laboratory measurements and record device/network conditions. Lazy-load 3D, render on demand, reuse geometry/materials, instance repeated entities, and adapt resolution; these are supported R3F optimization approaches. [D14] Avoid a continuous idle render loop. Target immediate local control feedback within 100 milliseconds while showing genuine pending server calculation. Set training and query budgets after measuring representative data sizes; never fabricate completion to meet a visual target.

UX-012  -  Demonstrate acceptance with linked evidence. At P0, exercise five complete journeys: import authorized data and inspect lineage; train and compare the three models; select an entity through 2D/3D and inspect matching charts; compute and save a feasible scenario; ask a grounded question and replay/export its evidence. Test 320-, 768-, and 1440-pixel layouts, Light/Dark/System, reduced motion, keyboard use, screen reader essentials, WebGL failure, zero/missing data, network interruption, and permission changes. Confirm exported values equal the analytical results. A provenance break must invalidate all dependent widgets. Cross-tenant or field-permission tests must cover chart tooltips and agent tools as well as APIs. Record each DAT, ML, and UX requirement as passed, failed, or blocked with evidence; do not label the product complete while primary interactions remain placeholders.

## Controlled experiment matrix

The primary question tests effective-date and amendment handling with forecasting and optimization fixed. The secondary question tests selective agent intervention. Compare the following conditions separately; each result must identify which component changed.

| Study | Comparison | Inputs held fixed |
| --- | --- | --- |
| F | Seasonal naive versus LightGBM versus quantile TCN | Cohort, origins, horizon, available covariates, simulator, constraints and costs |
| R1a | Vector retrieval versus hybrid lexical/vector retrieval | Agent policy, forecaster, optimizer, corpus, questions and source visibility |
| R1b | Hybrid retrieval versus the same hybrid retrieval with reranking | Candidate corpus, model/tool settings, questions and source visibility |
| R2 | Hybrid retrieval versus the same retrieval with explicit effective-date, amendment and conflict logic | Models, tools, source corpus and task set |
| R3 | Time-aware system versus the same system with an evidence-repair loop before action preparation | Retrieval candidates, forecasting, optimizer and mandatory execution controls |
| A | Always-invoked agent versus a declared selective-intervention policy | Same trained model, tool set, retrieval configuration, tasks and limits |
| O | Strong structured-policy optimizer reference | Correct policy inputs supplied directly; report that this bypasses document interpretation |

Tenant permissions, document ACLs, historical knowledge cutoffs and core execution safety checks remain enforced in every condition. Do not disable them to create a weaker comparator. Effective-date selection may vary only in an isolated read-only R2 research profile within the same set of authorized documents known at the decision time; external adapters are disabled in that profile. The operational product always enforces its full temporal rules. Evaluate proposal validity against held-out policy ground truth; keep that answer key inaccessible to the runtime agent. Report invalid proposals, rejected actions, repair attempts and executed violations separately. Zero executed violations caused by a backend rejection mechanism does not prove that retrieval proposals were accurate.

Separate development and final task sets. Group shared policy templates and demand trajectories in splits and uncertainty estimates. Freeze stopping rules, budgets, terminal inventory valuation and beyond-horizon order treatment before testing. Establish the specific contribution through a related-work comparison with inventory-agent research. [R1]
